# BitCar – Buyer-Seller Chat

## وثيقة مواصفات ميزة المحادثات بين المشتري والبائع

**المشروع:** BitCar – Flutter Car Marketplace
**الميزة:** Buyer–Seller Chat
**نطاق التنفيذ:** B1–B12
**الحالة:** منفّذة ومختبرة ومدمجة في الفرع الرئيسي main.

---

# 1. الهدف من الميزة

إضافة نظام محادثات داخل تطبيق BitCar يسمح للمشتري بالتواصل مع البائع مباشرةً للاستفسار عن السيارات المعروضة للبيع.

تعتمد الميزة على Firebase Authentication وCloud Firestore، وتستخدم BLoC لإدارة الحالة، مع الالتزام ببنية Clean Architecture الموجودة في المشروع.

الأهداف الرئيسية:

* توفير محادثات مباشرة بين المشترين والبائعين.
* منع تكرار المحادثات بين المستخدمين أنفسهم.
* توفير قائمة محادثات مع معاينة الرسائل وعدد غير المقروء.
* تحديث الرسائل وحالات القراءة بشكل مباشر.
* دعم تحميل الرسائل القديمة تدريجياً.
* دعم حالات الاتصال والانقطاع وإعادة المحاولة.
* توفير حذف الرسائل والمحادثات بطريقة آمنة.
* حماية خصوصية المحادثات ومنع الوصول غير المصرح به.
* منع تسرب بيانات المستخدم السابق عند تسجيل الخروج وتبديل الحسابات.

# 2. تصميم المحادثات

## 2.1 محادثة واحدة لكل مشتري وبائع

تعتمد الميزة على إنشاء محادثة واحدة فقط لكل زوج من المستخدمين (Buyer + Seller)، وليس محادثة مستقلة لكل سيارة.

مثال:

المشتري A يتواصل مع البائع S بخصوص سيارة BMW.

لاحقاً يتواصل A مع البائع نفسه بخصوص سيارة Mercedes.

في هذه الحالة:

* لا تُنشأ محادثة جديدة.
* تُفتح المحادثة السابقة.
* تظهر الرسائل القديمة.
* يستطيع الطرفان مناقشة جميع سيارات البائع داخل المحادثة نفسها.

يُنشأ معرّف المحادثة بطريقة حتمية اعتماداً على UID الطرفين بعد ترتيبهما، لضمان عدم تكرار المحادثات.

## 2.2 بدء أول محادثة

يظهر زر:

`Chat with Seller`

في صفحة تفاصيل السيارة، فوق زر الاتصال الهاتفي `Contact Seller`.

عند الضغط عليه لأول مرة:

* تُفتح شاشة المحادثة.
* تظهر رسالة جاهزة في حقل الكتابة.
* لا تُرسل الرسالة تلقائياً.
* يستطيع المشتري مراجعتها وتعديلها قبل الإرسال.

نص الرسالة:

`Hello, I'm interested in your <brand> <model> (<year>). Is it still available?`

لا تُنشأ محادثة جديدة بمجرد فتح الشاشة أو الرجوع منها دون إرسال رسالة.

عند إرسال أول رسالة، تُنشأ المحادثة والرسالة الأولى ضمن عملية ذرية واحدة.

إذا كانت المحادثة موجودة مسبقاً، تُفتح المحادثة نفسها وتظهر الرسائل السابقة.

# 3. واجهات المستخدم

## 3.1 Conversations List

تحتوي الشاشة على قائمة بجميع محادثات المستخدم.

تُعرض في كل عنصر:

* اسم الطرف الآخر.
* معاينة آخر رسالة.
* وقت آخر رسالة.
* عدد الرسائل غير المقروءة.
* مؤشر بصري لوجود رسائل جديدة.

تترتب المحادثات تنازلياً حسب `lastMessageAt`.

تدعم الشاشة:

* Loading State.
* Empty State بالنص `No conversations yet`.
* Error State مع Retry.
* Offline Banner.
* فتح المحادثة عند الضغط على العنصر.
* حذف المحادثة عبر الضغط المطوّل والتأكيد.

## 3.2 Conversations Icon

توجد أيقونة المحادثات في HomeLayout قبل أيقونة البحث.

عند وجود رسائل غير مقروءة:

* تظهر نقطة حمراء على الأيقونة.
* تختفي النقطة عند عدم وجود رسائل غير مقروءة.
* يعكس المؤشر حالة المستخدم الحالي فقط.

## 3.3 Chat Screen

تحتوي شاشة المحادثة على:

* اسم الطرف الآخر.
* قائمة الرسائل.
* حقل كتابة الرسالة.
* زر الإرسال.
* حالة الاتصال.
* حالة الإرسال والقراءة.

عند فتح محادثة موجودة من قائمة المحادثات يكون حقل الكتابة فارغاً.

## 3.4 Message Bubble

تُعرض رسائل المستخدم والرسائل الواردة بتصميم مختلف.

تدعم الفقاعة:

* نص الرسالة.
* وقت الإرسال.
* حالة الرسالة.
* الضغط المطوّل لعرض خيار Delete للرسائل المؤهلة.

# 4. إدارة الرسائل

## 4.1 حالات الرسائل

يدعم النظام الحالات:

| الحالة  | المعنى                     |
| ------- | -------------------------- |
| sending | الرسالة قيد الإرسال        |
| sent    | وصلت الرسالة إلى Firestore |
| read    | قرأها الطرف الآخر          |
| failed  | فشل إرسال الرسالة          |

يمكن إعادة إرسال الرسائل الفاشلة وفق قواعد إعادة المحاولة المعتمدة.

تظهر مؤشرات القراءة والإرسال على الفقاعات، مع توفير Semantics لدعم قارئات الشاشة.

## 4.2 تحديث الرسائل مباشرة

يستخدم التطبيق Firestore Streams لمراقبة أحدث الرسائل.

عند وصول رسالة جديدة:

* تظهر لدى الطرف الآخر مباشرةً.
* تتحدث معاينة آخر رسالة.
* يتحدث وقت آخر رسالة.
* يتحدث عدد غير المقروء.
* يتحدث ترتيب المحادثة في القائمة.

## 4.3 Pagination

لا يتم تحميل جميع رسائل المحادثة دفعة واحدة.

الآلية:

* تحميل أحدث 20 رسالة عند فتح المحادثة.
* مراقبة أحدث الرسائل باستخدام Stream.
* عند التمرير للأعلى، تحميل 20 رسالة أقدم.
* استخدام `startAfter([Timestamp, id])` لتحديد نقطة الاستكمال.
* منع تكرار الرسائل.
* الحفاظ على ترتيب `(createdAt, id)`.
* الحفاظ على موضع التمرير عند وصول رسائل جديدة أو تحميل رسائل قديمة.

تُدار الرسائل محلياً ضمن مجموعات:

* `liveMessages`
* `loadedMessages`
* `pendingMessages`

وتُدمج مع إزالة التكرار وفق أولوية البيانات الحية.

الرسائل المحلية المعلّقة أو الفاشلة لا تُحتسب ضمن حد العشرين رسالة المحمّلة من الخادم.

# 5. الرسائل غير المقروءة وحالة القراءة

تُدار حالة القراءة لكل طرف بصورة مستقلة.

تُستخدم الحقول:

* `unreadCount`
* `lastReadAt`
* `clearedAt`
* `otherLastReadAt`

عند وصول رسالة جديدة:

* يزداد عداد غير المقروء للطرف الآخر.
* تظهر النقطة الحمراء في واجهة المستخدم.

عند فتح المحادثة:

* يتم تعليم الرسائل كمقروءة.
* يُحدّث `lastReadAt`.
* يصبح عداد غير المقروء صفراً.
* تختفي النقطة الحمراء عند عدم وجود محادثات أخرى غير مقروءة.
* يرى المرسل علامة القراءة `✓✓`.

لا تُنفذ عملية تعليم القراءة إلا عندما تكون شاشة المحادثة ظاهرة، وتتوفر بيانات مؤكدة من الخادم، مع وجود رسائل غير مقروءة.

# 6. إدارة الأسماء العامة

توجد مجموعة Firestore باسم:

`publicProfiles`

يحتوي المستند العام على:

`displayName`

فقط، وتتم مزامنته مع الاسم الموجود في مستند المستخدم الخاص.

لا تتم مشاركة البريد الإلكتروني أو رقم الهاتف أو الدور الوظيفي ضمن هذه المجموعة.

عند تحديث المستخدم اسمه من Profile:

* تتم مزامنة الاسم العام.
* تتحدث بيانات الاسم المستخدمة في المحادثات.

إذا لم يكن للمستخدم ملف عام، يُستخدم الاسم البديل:

`BitCar user`

توجد آلية `FillOwnPlaceholderName` لاستبدال الاسم البديل بالاسم العام عند توفره، دون تأخير فتح المحادثة.

تُنفذ عملية الاستبدال بصورة غير متزامنة، ولا يؤدي فشلها إلى منع استخدام المحادثة.

# 7. التعامل مع الاتصال والأخطاء

يدعم النظام الاتصال والانقطاع عن الإنترنت.

## Offline Behavior

* الاستفادة من بيانات Firestore المحفوظة محلياً.
* إظهار Offline Banner بعد تأخير ثانيتين لتجنب الوميض.
* إخفاء الشريط عند عودة الاتصال.
* تعطيل الوظائف التي تتطلب كتابة غير متاحة دون اتصال.
* الاحتفاظ بالبيانات المحلية والرسائل المعلّقة حسب سلوكها المعتمد.

## Stream Errors

عند حدوث خطأ قابل لإعادة المحاولة:

* محاولة تلقائية واحدة بعد 3 ثوانٍ.
* بعد فشلها، يظهر زر Retry للمستخدم.

عند وجود خطأ صلاحيات نهائي:

* لا تستمر محاولات إعادة الاشتراك تلقائياً.
* تظهر رسالة الخطأ.
* يتم تعطيل الإرسال عند الحاجة.

تُحافظ الشاشة على الرسائل التي سبق تحميلها عند فشل Stream، ولا تفقد محتواها لمجرد انقطاع التحديثات المباشرة.

# 8. حذف الرسائل

يعتمد حذف الرسائل على Soft Delete وليس الحذف الفعلي من Firestore.

يستطيع المستخدم حذف رسائله فقط، ولا يستطيع حذف رسائل الطرف الآخر.

شروط ظهور Delete:

* الرسالة مرسلة أو مقروءة.
* الرسالة تخص المستخدم الحالي.
* الرسالة غير محذوفة.
* الاتصال متاح.

بعد تأكيد الحذف:

* تصبح `deleted = true`.
* يصبح نص الرسالة فارغاً.
* تبقى الرسالة في مكانها.
* تظهر العبارة:

`This message was deleted`

لا تظهر أيقونة حالة الإرسال أو القراءة للرسالة المحذوفة، ويظل وقت الرسالة ظاهراً.

## 8.1 الحذف الذري

يتم حذف الرسالة وتحديث المحادثة ضمن Firestore Transaction واحدة.

يُستخدم الحقل:

`lastDeletedMessageId`

لإثبات ارتباط حذف الرسالة بتحديث المحادثة.

يضمن Firestore Security Rules التحقق من الحالة السابقة واللاحقة باستخدام `get()` و`getAfter()`.

عند حذف آخر رسالة:

* تتحدث `lastMessage`.
* تصبح معاينة الرسالة المحذوفة بالنص البديل.

عند حذف رسالة غير مقروءة:

* ينخفض عداد الطرف الآخر بمقدار واحد فقط إذا لم يكن قد قرأها أو مسح المحادثة بعد تلك الرسالة.

لا يُنقص العداد إذا كانت الرسالة مقروءة بالفعل أو أُخفيت ضمن `clearedAt`.

تُمنع إعادة احتساب حذف الرسالة نفسها.

عند حدوث `permission-denied` أثناء عملية الحذف بسبب تغير الحالة بين القراءة والكتابة، يسمح التصميم بمحاولة إضافية واحدة بقراءات جديدة. لا تُعاد المحاولة عند الأخطاء الأخرى.

# 9. حذف المحادثات

حذف المحادثة لا يعني حذف سجل الرسائل من Firestore.

يستطيع المستخدم إخفاء المحادثة من قائمته بصورة مستقلة عن الطرف الآخر.

تعتمد العملية على:

`clearedAt.<uid>`

و:

`unreadCount.<uid>`

عند تأكيد الحذف:

* يُحدّث `clearedAt` للمستخدم الحالي.
* يُصفّر عدد الرسائل غير المقروءة الخاص به.
* تختفي المحادثة من قائمته.
* لا تتأثر قائمة الطرف الآخر.
* لا تُحذف الرسائل فعلياً.

تُعتبر الرسائل التي يكون `createdAt` الخاص بها أقدم من `clearedAt` أو مساوياً له رسائل مخفية عن هذا المستخدم.

عند وصول رسالة جديدة بعد `clearedAt`:

* تعود المحادثة إلى القائمة.
* تظهر الرسالة الجديدة.
* تبقى رسائل الطرف الآخر وتاريخه محفوظة.

تُنفذ العملية باستخدام Transaction، ولا تتسبب في كتابة معلّقة عند انقطاع الإنترنت.

# 10. الأمان والخصوصية

تم إعداد Firestore Security Rules لحماية المحادثات والرسائل.

أهم القواعد:

1. يجب أن يكون المستخدم مسجلاً للدخول للوصول إلى وظائف التطبيق.
2. لا يستطيع قراءة المحادثة إلا أحد المشاركين فيها.
3. لا يستطيع غير المشارك الوصول إلى المحادثة أو رسائلها.
4. لا تمنح صلاحية Admin أي تجاوز لخصوصية المحادثات.
5. يجب أن يطابق `senderId` هوية المستخدم الذي يرسل الرسالة.
6. لا يستطيع المستخدم تعديل أو حذف رسالة الطرف الآخر.
7. لا يستطيع المستخدم تغيير عداد غير المقروء للطرف الآخر دون تحقق القواعد.
8. لا يستطيع خفض العداد دون حذف رسالة حقيقي مرتبط بالعملية.
9. تحديث الرسالة والمحادثة المرتبط بالحذف يجب أن يكون ذرياً.
10. لا يمكن إنشاء صلاحيات إضافية بتعديل بيانات المستخدم من التطبيق.

تم إصلاح مشكلة R6 المتعلقة بإمكانية خفض عداد غير المقروء دون حذف فعلي.

اعتمد الإصلاح على التحقق المتبادل بين الرسالة والمحادثة باستخدام `getAfter()`.

تم نشر القواعد على مشروع Firebase الحقيقي:

`carshop-b79bc`

وأصبح إصدار القواعد المنشور مطابقاً لملف `firestore.rules` المحلي.

# 11. حماية الجلسات وتبديل الحسابات

تم تطوير `SessionGate` لمنع تسرب بيانات مستخدم إلى مستخدم آخر.

عند تسجيل الخروج:

1. فحص وجود كتابات غير متزامنة.
2. إذا وُجدت، تظهر نافذة تحذير.
3. يستطيع المستخدم اختيار Cancel أو Log out.
4. عند تأكيد الخروج، تُحفظ علامة `firestoreWipePending` أولاً.
5. تظهر شاشة `Signing out…`.
6. تُغلق بوابة الجلسة وتُلغى التيارات وتُمنع العمليات الجديدة.
7. يُنتظر انتهاء العمليات الجارية حتى 5 ثوانٍ كحد أقصى.
8. يتم استدعاء `terminate()`.
9. يتم استدعاء `clearPersistence()`.
10. يتم تسجيل الخروج من Firebase Authentication.
11. تُزال علامة التنظيف.
12. تُفتح البوابة.

## 11.1 استعادة الخروج بعد إغلاق التطبيق

إذا أُغلق التطبيق بعد حفظ علامة `firestoreWipePending` وقبل اكتمال الخروج:

* يقرأ `main.dart` العلامة قبل `runApp`.
* يستدعي `CompletePendingSignOut`.
* يحاول إيقاف Firestore وتنظيف بياناته.
* يكمل تسجيل الخروج.
* يمنع عرض بيانات الجلسة السابقة قبل اكتمال العملية.

إذا فشل تنظيف البيانات بعد نجاح تسجيل الخروج، تبقى العلامة ويُسمح بإعادة محاولة التنظيف دون تسجيل خروج جديد.

أما إذا فشل `signOut` نفسه، فتبقى البوابة مغلقة حتى إعادة تشغيل التطبيق.

إذا فشل حفظ العلامة قبل بدء الخروج، يتم إلغاء العملية ويبقى المستخدم داخل حسابه.

# 14. Firebase والقيود التقنية

تم تنفيذ الميزة بما يتوافق مع Firebase Spark Plan.

* Cloud Firestore: مستخدم.
* Firebase Authentication: مستخدم.
* Firebase Cloud Functions: غير مستخدمة.
* Firebase Cloud Messaging: لم تُضف إشعارات Push.
* لا يتطلب الحل الحالي الترقية إلى Blaze.
* لا توجد وظيفة خلفية ترسل إشعارات عند وصول رسائل جديدة.

التحديثات المباشرة تعتمد على Firestore Streams، وتعمل أثناء تشغيل التطبيق واتصاله بالخدمة.

إشعارات Android وiOS المستقبلية خارج نطاق التنفيذ الحالي.
